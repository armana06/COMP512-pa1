\section{Overview and Shared Architecture}

The goal of this assignment was to distribute a travel reservation system
implemented in Java. We were initially provided with a code template where a
single client was talking over RMI to a single \code{ResourceManager}
(\code{RM}) that stores all flights, cars, rooms, and customers in a single
hashmap. The system was first distributed with RMI, by inserting a middleware
between the (unmodified) clients and three \code{RM}s, one for each resource
type (Section~\ref{sec:rmi}). The system was then distributed using TCP sockets
(Section~\ref{sec:tcp}).

Both versions share a similar architecture. The client is unchanged and talks
only to a middleware server. The middleware dispatches every request to one of
the three RMs, one each for flights, cars, and rooms. Each RM runs the
\code{ResourceManager} class provided in the starter code (which implements the
whole \code{IResourceManager} interface), and the middleware only calls flight
methods on the flights RM, car methods on the cars RM, and room methods on the
rooms RM. The RMI version uses the \code{ResourceManager} class unchanged, and
the TCP version adds a \code{cancelReservation} operation (used to undo a
bundle) and a total line to the customer's bill.

\subsection{Customers}

In both versions, we chose to replicate customers on all three RMs so that each
RM holds a record for every customer, but each copy only contains the
reservations of that RM's resource type. This simplifies the code since every
reservation is a single call to one RM and we can reuse the template's
\code{reserveItem}: the function finds the customer, decrements the resource
count, and records the reservation in the customer's data, all in the same RM. A
reservation thus can't half-succeed, and this approach requires no change to the
RM code. The drawback is that creating, deleting, and querying a customer 
involves all three RMs. This means that a creation or deletion that fails after
only one or two of the RMs were updated leaves the copies inconsistent and must
be handled somehow. The total bill also needs to be assembled from the 3 RMs.

The specification also offers two alternatives to this design: store the customers
in an additional server or at the middleware, i.e. store all the customers at a
single place. This simplifies creating customers, queries about their reservations,
and computing the total bill (deleting a customer still involves every RM that
holds their reservations), but it separates the customers from the items they
reserve (every reservation must update two servers). While both designs may result
in operations that can fail halfway, and thus require an inconsistency to be
repaired, they differ when a server crashes: a crashed RM in our design only loses
its own items together with their reservations, whereas if the middleware or the
customer server fails, all customer data is lost.

\subsection{Bundles}

A bundle reserves one or more flights, and possibly a car and/or a room at a
location, for a single customer. Reserving a bundle is handled by the middleware
in both versions since it can involve up to three RMs (one per resource type).
A bundle must be all-or-nothing, i.e. either every requested item is reserved,
or none is. The difficulty in achieving that is that the template offers no way
to cancel a single reservation (deleting a customer would also cancel their
previous reservation). The two versions handle this differently (see
Sections~\ref{sec:rmi} and~\ref{sec:tcp}).


\section{RMI Distribution}\label{sec:rmi}

\subsection{Middleware and startup}

The middleware is implemented using only one class
(\code{Server.RMI.RMIMiddleware}) that implements \code{IResourceManager}.
Since the client interacts only with that interface, it connects to the
middleware the same way it would to an RM using \code{./run_client.sh <host>
  Middleware}. The middleware receives the hostnames of the flights, cars, and
rooms RMs as three command line arguments. On startup, it then looks up each of
the three RMs in the registry, retrying every 500ms until they all become
reachable. It only binds itself as \code{group_42_Middleware} after all the RMs
are connected so that a client can't reach the middleware if it's not fully
intialized. This also means that the start order of the processes don't matter.
The interface methods are just forward methods to the corresponding RM.

\subsection{Errors and exceptions}

When an RM is down or does not answer within 5 seconds, the middleware's call to
that RM throws a \code{RemoteException}. We chose not to catch this exception in
the middleware: RMI delivers it to the client wrapped in a \code{ServerException},
and the client already reports it by printing it as a command error with its
cause. If the middleware itself is down, the client automatically reconnects to
it and executes the command again.

\subsection{Customers}

As described above, customers are replicated in each RM and so the middleware
sends every customer creation, deletion, and bill query to all three RMs. To
create a customer, \code{AddCustomer} chooses IDs sequentially (via a counter kept
in the middleware), skipping any ID that is already taken (e.g. by
\code{AddCustomerID}), and creates the customer in each RM. If this fails for one
RMs, the customer is deleted from the RMs where the creation succeeded (safe since
the customer has no reservations yet) and the exception is propagated to the
client. Deleting a customer can't be undone (the interface has no way to restore
the reservations of the deleted customer), so the middleware calls
\code{deleteCustomer} on all RMs and throws an exception to the client if one
fails. The client then must run the command again to delete the remaining
customer (or else it'll be leaked along with its items).

\subsection{Bundle}

As discussed previously, the bundles must be all-or-nothing, but the provided
interface has no way of canceling a single reservation without wiping a
customer's previous reservations. The RMI version handles this by checking that
all the resources are available before reserving anything. This is done in three
phases (using the middleware's global lock):
\begin{enumerate}
\item Check that each argument is valid.
\item Pre-check that the customer exists on every RM involved in the bundle and
  that the resources are available. A failure at this stage returns \code{false}
  without doing anything.
\item Reserve the flights, and possibly the car and the room.
\end{enumerate}
The lock prevents other clients from modifying anything between the second and
third step, and so this operation never fails unless a RM fails during the third
part. If this happens, the middleware throws an exception to the client that lists
reservations that were made and the user must complete the bundle manually.

\subsection{Concurrency}

The middleware handles concurrent requests by using one global lock held by
every operation that may modify any state in a RM (the only operations that are
not locked are single item queries). This means that most operations are fully
serialized but it makes the implementation simpler. Because a RM could hang (not
crash) while holding the lock, we added a timeout (5 seconds) so that these
calls fail instead of blocking every client forever.

\subsection{Final version}

Our final version is the version developed with AI, which is the one described
above. The version written by hand had several issues involving concurrency, the
support for multiple RMs per resource type (which is a more general solution but
introduced several bugs), and other behaviour that didn't match the 
specification. Modifying this version would've amounted to a rewrite, only to
end up with a version that essentially mirrors the one developed with AI. Since
the AI version was relatively well tested, we chose to submit it as our final
version.

\section{Testing}

Listed below are some of the (more interesting) tests used to determine the
correctness of our implementations. Some tests are not listed explicitly so that
the list fits in one page, but a short description is provided instead. These
tests were conducted locally and on the machines in Trottier.

\textbf{RMI}
\begin{itemize}
\item \emph{Dispatch.} Resources are only stored on the RM of their type
  (checked by querying RMs directly).
\item \emph{Delete item.} Deleting an item only works once, deleting it again
  returns \code{false}.
\item \emph{Delete customer.} The count of all seat, car, and room are restored
  on all RM when deleting a customer holding resources.
\item \emph{Negative counts.} Command like \code{AddFlight,2,-5,10} returns
  \code{false} and the RM is never reached.
\item \emph{Price update.} \code{AddFlight,1,0,250} on an existing flight only
  changes its price (since the number of seats to add is 0). A customer who
  reserved a seat before a price update will only be charged the previous price,
  but if he reserves a new seat afterwards, he will be charged the new price for
  all his seats. Total bill is correctly calculated.
\item \emph{Bundle.} If a room is sold out, the bundle fails and the other
  resource counts remain unchanged. Bundles with non-existing customer or
  resource fail.
\item \emph{Customer IDs.} \code{AddCustomer} returns 1, \code{AddCustomer}
  again returns 2. After \code{AddCustomerID,3} and \code{AddCustomerID,5},
  running it twice returns 4, then 6. A duplicate ID returns \code{false}.
\item \emph{RM failure.} Commands involving a killed RM fail with an exception.
\end{itemize}

\subsection{Tokens}

For the RMI session, Claude estimates around 8-10 million input tokens and 140k
output tokens (for the conversation itself). For the TCP version, Copilot
reports about 9.8 million input tokens and 97k output tokens. In both cases,
most input tokens are the conversation being re-read on every request. In total,
we used roughly 18-20 million input tokens and 240k output tokens. 

\subsection{Some thoughts}

Both of us agree that the use of AI, while allowing us to finish the assignment
faster, greatly impaired our ability to reason about the code, even though we
``made the decisions''. It also left us with a relatively shallow understanding
of the concepts involved.

Overall, we would rather not use AI for future assignments, and postpone our
inevitable transition into professional meat proxies for LLMs.
